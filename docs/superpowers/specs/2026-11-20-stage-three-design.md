# 第三阶段：社区与内容治理设计

日期：2026-11-20。状态：业务规则经逐项讨论确认；以下数据模型、接口与批次衔接为据此提出的技术设计，尚未实现或验证。本文不是第三阶段验收结果，不取代第一、第二阶段的实际记录。

## 1. 目标、基线与实施顺序

形成社区交流、分区自治、治理申诉及专业审核闭环。沿用 Java/Spring Boot、MySQL/Flyway、Vue/TypeScript、现有身份权限、内容资源与版本，不另建平行的内容系统。Python 不承担本期专业裁决。

2026-11-20 代码核对：

- `content_resources` / `content_revisions` 已有资源身份、正式版指针、冻结版本及乐观锁。`PersonalCenterService` 已有文章草稿、提交、撤回和复制修订；公开查询与作者最新稿分开。
- `ReviewService` 已有来源、知识、文章审核；文章走 `community:moderate`，知识走 `knowledge:review`，当前未实现按医学主题授权和组合审核。
- 已有资源点赞、收藏、浏览历史及审核通知写入，不重复创建交互表。
- `community_sections` 当前只有扁平分区、名称、编码、启用和排序；种子有基础知识、方剂学习、学习交流。
- `community_comments` 当前正文原位存储，缺评论版本历史和公开/候选双指针；`community_reports` 未绑定被举报版本，不能满足本次规则。
- 前端已有文章编辑器、通用内容详情、个人中心和审核台；尚无完整社区列表、分区成员和评论交互模块。

已确认分三批，每批依次完成数据库/接口设计、实现、验收；全部通过后才认定第三阶段交付：

| 批次 | 交付范围 | 边界 |
|---|---|---|
| 一：社区基础 | 两级分区及基础管理、成员加入退出、讨论与文章、版本化评论、点赞收藏、个人中心联动 | 打好版本、权限及治理扩展基础；不宣称观察期自动治理、申诉和专业复用已完成 |
| 二：治理闭环 | 分区直建/审核分流、观察期、归档和交接、规则版本、举报、通知、申诉、文章转来源 | 专业核验任务先按缺少对应授权能力保持待处理，不用普通治理审核冒充专业审核 |
| 三：专业审核增强 | 范围授权、回避、独立复核、组合审核、人工块标注、结论复用、到期复核 | AI 仅辅助；不宣称实现自动医学判断 |

批次一可独立在本地验收；完整自建分区入口在批次二的资格、规则分流和观察期闭环通过后开放。中间批次不作为已具备完整治理能力的社区交付。

## 2. 内容、版本与交互规则

- 正常登录用户通过既有 `community:post` 权限发讨论、评论和举报；科普投稿要求 `community:article:submit`，审核通过后公开。
- 普通讨论及评论正常发布/修改立即公开，保留版本。命中明确高风险规则时，新版冻结待审；模糊提示不直接认定违规。
- 已公开内容产生待审修改时保留旧公开版。新版本通过才替换正式指针；公众不见待审标记、不因此降权、不刷新首次公开时间。待审内容不进入搜索、推荐或后续 RAG 索引。
- 初次发布待审无公开版。旧公开版本身存在阻断风险时，可隐藏整条后复核。作者修改不能自行解除治理下架。
- 提交后冻结，撤回后生成新稿再检查，不能把原待审快照改为普通内容来绕过检查。同一内容只保留一个当前待审任务，历次提交/撤回及关联保留。
- 评论两层展示：根评论与根下回复；回复对象可以是同串任意评论，但必须同帖子、同根。删除父评论保留安全占位和后续回复，不公开被删正文。
- 每篇帖子只归属一个一级或二级分区。一级列表汇总直属与下属内容，支持分区和内容类型筛选；不能重复累计同一资源。
- 子分区归档只读，禁止新帖及新评论，已有公开内容保留原分区标识并在一级列表可见；关闭新增互动不能妨碍举报、申诉、作者删除及治理处置。
- 文章转来源固定 `origin_revision_id`，独立经过来源审核和知识加工。社区公开不是 RAG 入库资格。

### 2.1 第一批文本格式与渲染约束

- 帖子和科普文章采用受控 Markdown，评论采用纯文本；第一批不支持图片上传、附件或 Markdown 外部图片嵌入，不自动请求外部媒体。该范围为本次讨论确定的文本优先方案。
- Markdown 允许语法由管理员在系统实现的安全能力集合内配置并版本化，记录变更人、时间及原因；原始 HTML、脚本、事件属性和可执行嵌入为不可配置的禁止项，不因管理员放宽白名单而开启。
- 提交版本保存原始内容及当时格式策略版本，解释语法限制有据可查。公开渲染同时服从当前安全约束，策略更新不能让历史内容绕过安全限制，也不得为重渲染而覆盖历史源文本；必要时记录策略更新对历史展示的影响。
- 链接仅允许明确列出的协议；第一批建议限于 `http`、`https`，其他协议默认拒绝，`mailto` 如需支持须显式增加策略。外链设置 `rel="nofollow ugc noopener noreferrer"`；URL 和 HTML 输出分别按相应上下文处理，不能只依赖禁用原始 HTML。代码块按转义后的文本显示，禁止执行。
- 评论只按文本输出并转义，不使用富文本或 Markdown 渲染，不将用户正文传入可执行 HTML；不因纯文本而省略高风险暂存、版本、举报和申诉流程。
- 版本差异以服务端保存的源文本为事实依据，块级映射、渲染预览及视觉差异只是辅助。渲染结果相同不能认定源文本未变或自动复用审核意见；块拆分/合并或映射不确定时按既定回退规则处理。
- 待审版差异仅作者、具备对应任务访问权限的治理/专业审核人员可见，公众接口不返回候选正文、摘要、源文本或差异。编辑命中规则仍保留旧公开版，新版暂存；旧版自身触发阻断风险时另行隐藏。
- 服务端按内容类型限制标题、正文长度和请求体字节数，并限制创建、修改和重提频率，前端提供同口径提示。拒绝超限请求不得产生半份版本或审核任务；正文不静默截断，频率限制返回明确的重试等待信息，阈值与策略版本留痕。长度初值见下节；频率、请求体字节及文献数量/长度的具体初值仍需在实施设计中明确，不将未确认数值记为已确认门槛。
- 验收覆盖策略版本可追溯、管理员不能启用禁止能力、危险协议/混淆链接被拒绝或安全处理、代码块不执行、HTML/脚本在评论中仅显示文本、渲染相同但源码不同仍产生差异、待审差异越权不可读，以及长度/频率限制的事务完整性。

### 2.2 文本长度、参考文献与长文扩容

已确认的默认可配置上限：标题 120 字符、普通讨论正文 20,000 字符、科普文章正文 100,000 字符、单条评论或回复 2,000 字符。前后端使用统一字符计数口径，另外校验请求体字节数；具体计数实现须在接口契约中写清并覆盖中文及表情边界，不让浏览器提示与服务端判定不一致。已有超限历史内容保留可读，不因新增长度策略自动删除或隐藏。

- 科普文章支持独立参考文献条目，包括题名、作者、年份、出处、DOI/链接及引用位置；文献不挤占正文字符额度，但有独立数量、字段长度和请求体字节限制。外链继续受协议与渲染安全策略约束。
- 第一批参考文献由作者手动录入，正文通过 `[1]` 等编号关联，点击后跳转本页对应文献。正文与文献关系保存稳定条目标识，编号是该文章版本内的展示顺序；重排文献须同步更新编号映射，删除仍被引用的条目时提示修正引用，不可让原编号静默指向另一文献。
- 本期不自动抓取 DOI/链接目标，不自动补全文献、下载全文或核验真实性；手动填写不显示为已核验。文献跳转属于文章内定位，访问外部出处仍受既定链接策略约束。
- 文献及其正文关联随文章版本保存、冻结、对比和审核；修改文献不得原位改变旧公开版或既有审核证据。删除、重新排序引用应能检查对应关系，不能让旧版本引用指向另一篇文献。
- 正文中引用的原文段落仍计入正文字符数，参与风险检查、版本差异与专业审核，不能通过引用语法绕过长度或治理限制。填写参考文献不等于依据已经核验，也不等于具备知识入库资格。
- 编辑器显示已用字符数与当前额度，接近上限提前提示，并支持草稿分次保存；分次保存不豁免最终版本额度或请求体限制。校验失败保留编辑内容，不能静默截断或丢失草稿输入。
- 超过默认正文额度时，作者可针对已建立的文章身份申请扩容，填写原因；管理员批准该文章的新额度，记录申请人、审批人、原因、额度和时间。审批不会增加其他文章额度，不附带投稿权限，不代表内容审核通过。
- 扩容上限及超长请求处理仍需有受控的系统边界，审批界面只能在该边界内调整，不能写入无限额度。正文超额时保留已有草稿，并可从该文章申请扩容后继续编辑；建议拆分系列但不强制拆分完整论证。
- 现有 `PersonalCenterDtos.ArticleInput` 使用 `@Size(max=100000)` 的固定限制，第一批须将新旧投稿、草稿、修订和提交入口统一接入文章级额度检查，避免审批成功后仍被旧 DTO 拦截，或通过兼容接口绕过额度。正文额度扩大时同步校验传输及存储边界。
- 验收覆盖默认与文章例外额度、跨文章不能借用、无审批不能越限、新旧入口一致、长文不截断、独立文献限额、正文引文计数、文献冻结/差异/引用关系，以及额度审批不改变内容审核状态。
- 参考文献验收补充：正文编号可定位到本版本条目，重排不串引、删除被引条目需修正、无效引用可见提示、旧版引用不随新版变更，输入 DOI/链接不触发远程抓取或产生真实性核验标记。

## 3. 两级分区与生命周期

### 3.1 层级、创建及命名

- 一级核心大区仅管理员维护，名称围绕中医基础、中药与方剂、养生科普、学习交流；现有一级数据通过增量迁移兼容，不删除重建。
- 普通二级分区达到门槛直建后进入观察期；高敏感或高资源主题先申请审核。最多两级，不能挂到二级分区下。
- 创建者注册满 7 天、账号正常且未被限制建区、至少有 3 篇当前公开帖子，每人最多拥有 1 个观察期分区。阈值后台配置，判定时记录实际值与配置版本。
- 规范化名称完全重名拦截；同义/相似主题提示已有分区，不能仅凭相似度自动合并。改名或更换大区须审核。
- 分区合并由人工确认，保留迁移记录、内容归属来源和旧入口跳转；优秀分区可认证为官方，认证与层级分开，不自动变成一级大区。

### 3.2 成员与观察期

- 自由加入退出，不以加入作为正常浏览、发帖或评论前提；创建者自动加入。加入/退出幂等，退出不删除或隐藏历史内容。
- 有效成员为当前已加入、账号正常且未受社区参与限制者。仅受建区限制不影响普通成员身份；账号禁用后撤销加入状态，解禁不自动恢复，需要重新加入。
- 观察期 7 天。转正要求至少 5 名有效成员，其中至少 3 人注册满 7 天；至少 3 名不同有效成员在本分区合计有 5 篇当前公开、未删除、未下架的有效帖子。
- 待处理举报暂缓转正，不按举报数量直接认定违规；驳回后继续判断。首次未达标延期 7 天，再未达标归档；举报待处理的暂缓状态与活跃度未达标分开记录，避免被举报本身触发处罚性归档。
- 转正保存统计时点、成员资格、注册时间、作者与帖子集合及规则版本快照。之后正常退出、禁用或删帖不追溯撤销转正；发现刷量另走治理。
- 连续 30 天无新帖，提前通知后转为只读归档，保留内容，支持申请恢复；重复分区不自动强制合并。上述期限/阈值均可配置。

### 3.3 负责人、接管及交接

- 创建者有本分区简介/规则维护和置顶权限，可提交治理建议；没有下架他人内容、举报裁决、账号限制、分区合并或专业审核的额外权限。
- 本期单负责人，区分历史创建者与当前负责人，保留未来多人管理扩展点；不提前实现多人管理。
- 转让须接收人同意、满足建区资格、为本分区有效成员，并经管理员确认。接收观察期分区同样受每人最多 1 个观察期分区约束。
- 主动退出前转让或交回平台；禁用立即撤销管理权限并接管，解禁不自动恢复负责人身份。
- 若支持账号注销，注销时选择转让或交回，未完成交接自动交回，不阻塞注销。此规则不代表本期增加完整账号注销功能；保留内容并按账号隐私规则处理作者身份。
- 平台接管可代发公告、处理举报、交接和归档，不能跳过主题变更审核。无主状态与公开/归档状态分开。
- 无主时暂停观察期及延期，记录剩余时长，接任后恢复。接管最多 14 天，仍无人接任则只读归档；观察期创建者退出视为放弃管理，同样适用。

## 4. 规则分流、举报与申诉

### 4.1 规则与风险主题

管理员维护主题范围、适用对象、触发条件、例外、处理动作、理由类别及版本，命中记录保存当时规则与例外快照。初始主题覆盖医疗宣称、个体化诊疗建议、药材/产品、资质身份、争议对立、隐私案例。识别语境，区分引用批驳与自身宣称、教材介绍与个人指令、知识讨论与交易导流、学术讨论与攻击、脱敏案例与可识别健康信息。

规则用于分区申请、帖子、评论和编辑；明确高风险暂存待审，模糊匹配仅提示/进入治理队列。漏判可公开后隐藏复核，紧急情况可先隐藏后补齐复核。规则命中不等于违规；暂存和误判不影响账号信誉，频率限流依据行为单独判断。无 AI 或无对应专业人员不伪造核验结果、不自动放行。

### 4.2 举报和决定

- 举报固定当时可见的内容版本；普通用户不能借举报接口访问待审或私有版本。举报随版本替换仍有效，治理台对照旧公开版和候选版。
- 处理决定保存目标版本、规则依据、理由类别、处理人、动作、状态及前后关联；通知作者并提供申诉入口，举报者收到相关结果，不泄露私密材料。
- 所有提交、决定、通知使用事务和幂等键；并发相反决定只有一次生效，过期提交返回 409，不覆盖新状态。

### 4.3 申诉

- 通知后 7 个自然日内可申诉；逾期保留受理申请入口。每个决定一次正式申诉，同案最多两轮，案件 ID 贯穿调整后的新决定，不因新增决定重置次数。
- 首轮撤销或维持结束常规申诉；首轮调整可针对新决定二次申诉并重新起算窗口；第二轮结论终结常规申诉。新证据/处理错误允许治理侧启动独立纠错重审并留痕。
- 申诉针对原决定的固定版本，新编辑走新检查。原处理人不能裁决本人决定的申诉，涉及本人或利益冲突必须回避。
- 3 个工作日作为内部处理目标；工作日历和人员配置完善前不承诺保证时限。超时提醒/升级，无合格人员保持待处理，申诉不自动恢复公开。
- 防滥用限频单独给理由和复核入口，不能仅以申诉失败认定恶意。记录撤销/调整及原因，区分原判错误、新证据和规则变化。

## 5. 专业授权、组合审核与复用

- 专业范围按“主题域＋操作类型”人工核验并独立授权，可一人多范围；保存依据、核验人、有效期和变更。资质或机构变化、利益冲突时暂停/撤销，到期未复核不可审；期限按范围配置，不把用户举例的 1—2 年误记为已确定的统一期限。
- 专业授权与治理权限分离；治理角色不代表医学资质。记录师生、商业和任职等利益冲突并回避；超范围转审并保留意见。
- 医学事实、证据充分性与适用条件的专业结论对治理有约束；是否违规及处置尺度由治理结合上下文决定。不能把引用错误观点进行批驳直接等同于传播错误观点。
- 高敏感案件两名有对应治理资格且未参与原决定的人员背对背复核，提交前互不可见；分歧交有相应权限的负责人裁决并记录理由。所需专业意见独立于这两名治理人员计数，兼任须同时满足授权和回避。
- 单范围由合格人员审核；多范围仅背景提及时不机械双审。多个范围涉及实质建议或高敏感判断时拆项，各范围分别出意见；组合本身有新风险时增加组合关系审核，不能简单拼接单项通过。
- 普通案件一人持有全部所需授权可分别出意见，高敏感仍须满足双人独立复核。必审范围缺人、阻断结论或未解决的专业分歧时，不以多数表决整体放行。
- 本期人工标注内容块、主题、关联和结论前提；未标注默认不复用。块级差异、关联提示仅辅助，对应范围审核人最终确认，跨范围分别确认。
- 修改块必重审；缺少关联、影响不确定、前提变化、意见到期等情况回退关联块或对应范围整体重审。块映射不确定不自动继承。
- 按范围配置复用有效期，90 天是初始流程参数；规则、证据或关联前提变化可提前失效。复用不续期，只有新的实质审核产生新意见和有效期。
- 原意见不可变，独立关联记录新版本中的复用、替代或失效部分，记录标注/确认人、依据和时间。作者可查看复用/重审范围，申诉绑定新版本决定。
- 普通到期进入复核队列，保留既有公开内容；明确阻断风险或关键依据失效时先隐藏再复核。
- AI 只可提供提示，建议关联关系经人工确认后生效；不得自动认定复用、确认关联、放行或代替专业判断。后续扩大辅助范围须有样本、一致率、误判率和回退率的可追溯评估，不预设未经验证的达标指标。

## 6. 第一批数据设计建议

第一批字段、约束、迁移兼容、状态与事务，以及请求/响应契约细化见 [第一批数据库与接口详细设计](2026-11-20-stage-three-batch-one-data-api-design.md)。两份文档均为待实现设计；具体工程初值与业务已确认阈值在详细设计中分别注明。

只增量迁移，不修改已执行 V1—V6。以下是逻辑设计，实际 DDL、约束名称、索引及迁移序号在第一批实施计划中明确；不得据此声称已经执行迁移。

| 对象 | 设计及约束 |
|---|---|
| `community_sections` 扩展 | `parent_id`、规范化名称、创建者/负责人、生命周期、接管状态及乐观锁；父项必须一级；启用、观察/正式/归档与无主状态区分；名称按同父级规范化去重 |
| 新增 `community_section_members` | 分区/用户唯一，加入状态、加入/退出时间、原因、版本；退出保留记录，再次加入更新当前关系并追加事件 |
| 新增 `community_section_events` | 记录创建、入退、负责人和生命周期变更；操作者、幂等键、前后值、原因和时间 |
| `community_post_profiles` 扩展 | 复用唯一资源绑定和分区外键；增加最近公开编辑时间及列表所需索引；避免把待审更新时间作为公开排序字段 |
| `content_resources` / `content_revisions` | 复用正文和正式指针；普通讨论直接发布记录发布途径，不伪装为人工专业审核；已公开版本不可原位修改 |
| `community_comments` 扩展 | 作为评论身份，保存根评论、指定回复对象、作者、可见状态、公开/候选版本指针及乐观锁；根与回复同资源同串 |
| 新增 `community_comment_revisions` | 评论/版本号唯一，正文、状态、基准版本、创建/提交时间；提交及公开后冻结。历史评论回填为首个公开版本后切换读取，不能新旧正文两处各自可写 |
| 后续举报扩展 | 帖子举报关联同资源的 `content_revisions`，评论举报关联同评论的版本；兼容现有二选一目标约束，不能仅存会随编辑变化的正文引用 |

二批再引入政策版本、观察期快照/定时任务、交接申请、分区合并跳转、治理决定链、申诉及规则命中记录；三批再引入范围授权/回避、独立意见、审核块/关联/复用记录。每批迁移升级后仍可读取原有账号、文章、收藏与历史。

### 权限与一致性

- 沿用 `community:post`、`community:article:submit`、`community:moderate`；建议单独增加分区系统管理权限，不让账户管理员自动获得专业或治理裁决权。负责人权限按分区关系判断，不授予全局角色。
- 分区成员幂等加入/退出；内容发布、修改与评论核验本人所有权、分区状态、账号状态、版本及回复归属。归档与发帖竞态以同一分区锁序协调。
- 新社区事务拟按账号 ID 升序、分区 ID 升序、资源 ID 升序、评论/审核目标顺序锁定；接入现有来源转换/专业发布前对照既有来源→资源→审核锁序，不能在锁内倒序补取账号或分区锁。
- 创建门槛与每人观察期分区上限最终须在同一事务核验，不能只前端限制或先查后插。定时任务保存统计截止时点和政策版本，重复执行不重复转正、延期或通知。
- 同时保留公开版与作者最新稿，统一公开可见性判定用于列表、通用资源、用户主页、点赞收藏、搜索和后续推荐；受限正文不能通过摘要、历史或通用接口泄露。

## 7. 第一批接口与页面建议

外部统一 `/api/v1`，沿用身份、ApiResponse、分页和错误格式，ID 字符串、UTC 时间。以下新增路径为设计建议；已存在的个人中心文章及资源交互接口保留兼容。

| 接口 | 用途及边界 |
|---|---|
| `GET /community/sections`、`GET /community/sections/{id}` | 两级结构、当前用户加入状态及能力；只返回可浏览信息 |
| `PUT/DELETE /community/sections/{id}/membership` | 本人加入/退出，幂等；负责人退出引导交接，不静默抹去负责人 |
| `GET /posts?sectionId=&includeChildren=&type=&q=&sort=&page=&pageSize=` | 正式版列表；一级汇总去重；排序白名单，稳定 ID 次序兜底 |
| `POST /posts`、`GET /posts/{id}` | 创建讨论及读取公开详情；写入分区、正文和版本。文章沿用 `/me/articles` 草稿链并补充分区绑定 |
| `POST /posts/{id}/revisions` | 基于客户端所见版本产生新修订，携带幂等键和版本；过期冲突 409，不能覆盖后来版本 |
| `GET/POST /posts/{id}/comments` | 分页读根评论/回复及新增评论；服务端核验资源、分区、根和回复对象，拒绝跨帖或跨串回复 |
| `POST /comments/{id}/revisions`、`DELETE /comments/{id}` | 本人评论修订或删除占位；正文历史只对作者及具备权限的人员开放 |
| 既有 `PUT/DELETE /resources/{id}/like`、`.../bookmark` | 复用有效计数和幂等；资源不可见时不能新增互动，不泄露旧正文 |
| 建议 `/admin/community/sections` 管理入口 | 一级分区创建/编辑/停用及指定负责人；不得绕过二批的主题变更审核 |

第一批页面采用现有深绿界面体系：社区入口、一级汇总/子分区页、帖子详情与评论、讨论编辑器、既有文章投稿入口、我的加入分区及基础管理。详情只加载一次资源正文与浏览历史；回复/点赞等附属请求不增加浏览次数。375/1440 CSS px 检查列表、评论串、编辑器和管理表单，不引入水平溢出。
